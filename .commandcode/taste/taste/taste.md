# Taste
- Prefers tool configuration and context files (e.g., the `.commandcode` folder with taste preferences and settings) to live inside the relevant project/chapter folder rather than at the repository root — keeps each chapter self-contained and the repo root free of hidden tool folders. Confidence: 0.8
- Expects the assistant to actually run the built application locally and verify it works (install deps, smoke test, boot the server) before reporting completion — not just leave the code written but untested. Confidence: 0.8
- Prefers to create and manage the `.env` credentials file himself; expects the app to read his existing `.env` keys as-is (aliasing internally to canonical names) rather than renaming or restructuring his file. Confidence: 0.7
- Prefers application code to live inside a `src/` folder within the chapter, separate from docs/prompts. Confidence: 0.6
- Wants external service integrations (LLM providers, APIs) verified against the live endpoints during testing — real connectivity checks and actual generation calls, not just import/smoke tests. Confidence: 0.8
- Prefers to personally verify the running app (e.g., check the live connections himself through the UI) — when he asks to run the application, leave it running for his own checks rather than stopping it right after automated verification. Confidence: 0.8
- Cares about credential/secret hygiene — accepts and expects remediation when real secrets are found in tracked or template files (scrub `.env.example` down to placeholders, gitignore env files) rather than leaving credentials exposed. Confidence: 0.7
- Prefers radio buttons over selectboxes for binary/mutually exclusive choices in Streamlit UI — explicitly asked to change a selectbox to a radio button for provider selection. Confidence: 0.7
- Wants live service health/status indicators visible in the application UI (e.g., Ollama connectivity check, Groq key presence) — not just backend verification, but user-facing status panels. Confidence: 0.7
- Prefers the LLM to infer missing information from available context (e.g., Jira ticket summary/description) rather than asking the user for it — expects end-to-end generation without manual intervention. Confidence: 0.8
- When duplicate/redundant files are found, prefers to move them into a dedicated `duplicate/` subfolder within the chapter rather than deleting them — keeps originals accessible for reference. Confidence: 0.7
- Expects naming consistency between folder names and internal configuration names (e.g., skill name in frontmatter should match folder name pattern with proper hyphenation) — values clean, readable naming conventions. Confidence: 0.7
- Prefers test plans to include a gap analysis section with explicit questions for the author, prioritized test scenarios (P0/P1/P2) mapped to acceptance criteria and business rules, and a human review gate listing assumptions and open questions blocking sign-off. Confidence: 0.7
- Wants generated artifacts (test plans, deliverables) saved into the relevant project directory (e.g., `SkillMasterClass/skills/test-plan-generator/examples/`) — not just in the Command Code plans folder — so they are co-located with the project. Confidence: 0.8
- Prefers brief, concise answers to simple questions — rejects verbose multi-section explanations when a short direct response suffices (e.g., "no why" to a lengthy numbered breakdown). Confidence: 0.8
- When given a spec/requirements file, expects the assistant to BUILD the application first, then create a test plan for it — not just generate documentation or plans without implementation. Corrected the assistant when it only produced a test plan instead of building the app. Confidence: 0.9
- Uses a protocol-driven workflow via a `BLAST.md` file in each project folder — references numbered protocols (e.g., "go with protocol 0") as the entry point for new work. Expects the assistant to read BLAST.md first and follow the protocol step-by-step rather than improvising. Confidence: 0.85
- Mandates a consistent 4-file documentation structure at the start of each project: `task_plan.md` (checklists & goals), `findings.md` (research findings, curl/API requests), `progress.md` (time-stamped work log), and `LLM.md` (schema/rule/architecture reasoning). Wants these files created and maintained throughout the project. Confidence: 0.9
- Wants `progress.md` logged with fine-grained time intervals (every 10/30 minutes or hourly) including what was done, errors encountered, and results — values a detailed, time-stamped audit trail over a high-level summary. Confidence: 0.85
- Enforces strict folder scoping using `@file:folder` references in the prompt — expects the assistant to operate only within the specified folder and not touch files outside it. Confidence: 0.8
- Wants `findings.md` to capture concrete technical artifacts — including actual curl commands, API request samples, and external service interactions — not just narrative conclusions. Confidence: 0.75
- Prefers **GROQ** (`openai/gpt-oss-120b` on groq.com) as the LLM provider for agent/AI tasks — explicitly names GROQ and the open GPT 120B model when requesting LLM-powered features. Confidence: 0.85
- Prefers a **simple chat-style UI** where the user types a natural-language prompt like "Fetch PROJ-123 and create a test plan" rather than filling out structured forms — wants key parameters parsed from the prompt via regex, not collected via input fields. Confidence: 0.8
- Wants a dedicated **Settings page** in web apps that includes: API credentials input fields (Jira domain/email/token, GROQ key), **test connection buttons** for each external service that ping the live endpoint and report back, and a **default Jira key** field pre-filled in the main prompt. Confidence: 0.85
- Asks to execute multi-phase builds (e.g. "do phase 1, 2, 3, 4 and everything in one go") in a single end-to-end run rather than stopping for approval between phases — expects comprehensive execution once a plan is approved. Confidence: 0.75
- Explicitly instructs to **continuously update all memory files** (findings, progress, task_plan, LLM.md) at every milestone during a build, not just at the end — wants the audit trail kept current as work progresses. Confidence: 0.85
- For Web apps, prefers **vanilla HTML/CSS/JS with no build step** over React/Vue/Webpack — chose FastAPI + plain static files for a clean local-runnable setup. Confidence: 0.7
- Projects often reference a **"cyber side" / Gronth domain** (e.g., a Jira key for the Gronth/Kanban cyber project, confirmed working instance `kishorkuyate.atlassian.net` with key `KAN-1`) — values the assistant recognizing these internal project references and wiring them in as configurable defaults rather than asking what they mean. Confidence: 0.7
- Communicates in a casual, terse style with typos and lowercase (e.g., "what is the prohress", "i have updated the .env file can you please check and run") — expects the assistant to understand intent without demanding perfectly-formed prompts and to match with concise, direct replies rather than verbose restatements. Confidence: 0.75
- Wants the dev server **left running after automated verification** so he can personally interact with the UI and test live connections himself, rather than stopping the process once smoke tests pass. Confidence: 0.8
